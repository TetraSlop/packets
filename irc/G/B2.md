# B2 Inventory editor

B2 carries the session messages of the shop service
([services.md](../services.md#shop-service)) and of the two event
services, framed as every family `G` message is in
[envelope.md](../envelope.md). The shop uses B2 to sell packs, buy cards
back and take discards and deck edits after a [B0/00](B0.md#b000-shreq)
entry ([shop.md](../../flows/shop.md)). The Prize Center uses B2 to
announce awards and exchange prize points for one of thirty fixed cards
after a [70/00](70.md#7000-cvreq) entry
([prize-center.md](../../flows/prize-center.md)). The auction collection
uses B2 to deliver settled auction money and cards after a
[B0/01](B0.md#b001-shreq) entry ([A.md](../A.md#sequence)). The event card
service ([services.md](../services.md#event-card-service)) uses B2 to hand
out the cards and money an event awarded
([event-cards.md](../../flows/event-cards.md)). The event match service
([services.md](../services.md#event-match-service)) uses B2 to collect the
five cards a player borrows for an event round
([event-matches.md](../../flows/event-matches.md)). The same subtypes serve
every service; where a body or a rule differs the section has one
subsection per service. Pack contents, prices and the money and points
formulas are in [catalogue.md](../../client/catalogue.md); the trade reuses
the edit records on its own opcode, [A2](A2.md).

The wire has no error message. A malformed request, a wrong sender, a
stale session or an unowned card in an edit is a protocol violation; a
server closes the connection and the client reloads its profile on
reconnect. Only Buy has a negative answer, `@Card=/S=0`.

## B2/07 CardSelect

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| C2S | event match service | session number | `Select` on the same subtype, below | `struct EventCardSelect`, `struct Select` |

```c
struct EventCardSelect {
    uint32_t C;           // card count, 5
    struct {
        struct Card D;    // eight-field card: model, attack, type, physical, magical, points, arrows, deck
    } N[5];               // @N0..@N4
};

struct Select {
    uint32_t A;           // 1 confirms the selection
};
```

```
C2S GTM0GB2000701@CardSelect=/C=5@N0=/D=12|3|0|4|5|6|7|255@N1=...@N4=...
S2C GTM0GB2000701@Select=/A=1
```

`struct Card` is defined in [rules.md](../../client/rules.md#card-record).
The five cards must be owned with correct multiplicity. The `Select` reply
confirms the selection; the client then waits for the
[EQuit](#b217-quit) reply before returning to the room. The client moves
the selected cards out of its collection for the selection screen and puts
them back locally on both confirm and cancel before EQuit; no card return
message exists. Used only by event matches, see
[event-matches.md](../../flows/event-matches.md#sequence).

## B2/10 Erase

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| C2S | service of the open session | session number | none | `struct Erase` |

```c
struct Erase {
    uint32_t Mode;                    // 1 discards, 2 is the completion marker of the overflow editor
    uint32_t C;                       // record count, 1..15; absent when Mode is 2
    struct { struct CardReduced D; } rec[15];   // sections @0..@C-1, one reduced card each; absent when Mode is 2
};
```

```
C2S GTM0GB2001001@Erase=/Mode=1/C=1@0=/D=142|22|1|33|45|51
C2S GTM0GB2001001@Erase=/Mode=2
```

| Mode | Record | Effect |
|---|---|---|
| 1 | reduced 6-tuple | Discards one owned copy per record, no credit |
| 2 | none | Completion marker from the overflow editor; deletes nothing |

Erase, Sell and Decks are edits: they carry numbered records and have no
reply. Each record is a reduced 6-tuple (`struct CardReduced` in
[rules.md](../../client/rules.md#card-record)). A server matches records
against owned cards by value; a record that matches no remaining copy makes
the whole message invalid. Batch sizes are at most 15 records per Erase or
Sell and 13 per Decks (unverified). The same body is sent in the shop, the
Prize Center, the auction collection and the event card claim.

## B2/13 Init

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| S2C | the service entered, one subsection per service below | status: 1 means the service refused entry and the client leaves; any other value (0 is sent) accepts | none | per service, below |

Init opens a session. `N` is the session number that every later request
of the visit repeats in its argument and in `/No`. The client records the
sender and accepts later messages of the visit only from it. The services
number sessions independently, so a server routes a B2 message by which
session is open for the account, never by the argument alone.

### Shop

```c
struct ShopInit {
    uint32_t N;           // session number, 1..255
    uint32_t RA;          // rating
    uint32_t M;           // money, at most 99,999,999
    uint32_t CP;          // collection points, 0..65535
    uint32_t S;           // card count, 0..1000
    uint32_t SP;          // category written over pack 5, 0..3
    uint8_t  SN[7];       // name written over pack 5, hex; empty keeps the catalogue name
    uint32_t CMP;         // 1 makes the HD packs purchasable (category 1), 0 shows them as unavailable (category 4)
    uint32_t HD[79];      // count, then that many pack indexes to rewrite, each below 78
};
```

```
S2C GTM0GB2001300@Init=/N=1/RA=0/M=10000/CP=35/S=3/SP=0/SN=/CMP=0/HD=0
```

Sent after [B1/00 ShEnter](B1.md#b100-shenter). The client rewrites its
pack table from `SP`, `SN`, `CMP` and `HD`, then maps guild categories
7..9: guild 0 sees all three guild packs, guild 1..3 only the one whose
category is `6 + guild`. `SN` longer than 7 bytes is truncated unusually
(the client keeps `length - 7` bytes), so a visible special pack needs a
1..7 byte name.

The visible list contains packs with category 1 or 3, plus category 2
(Pauper's Pack) only while the player owns fewer than 5 cards and less
than the Beginner's Pack price, 1000 T. Categories 0, 4 and 5 are never
offered. Prices are not on the wire; the client reads them from its
catalogue.

Server choice: a server sends `SP=0/SN=/CMP=0/HD=0` by default, hiding
pack 5 and the FFX packs; the visible rank_1 Pack may be named after the
previous week's prize-money leader.

### Prize Center

```c
struct ExcInit {
    uint32_t N;           // session number, 1..255
    uint32_t PP[4];       // point balance before awards, then the Top 30, Lucky and Rookies awards, each award at most 65535
    uint32_t LC[3];       // Lucky Card models to announce; 65535 is no card
};
```

```
S2C GTM0GB2001300@ExcInit=/N=3/PP=1200|0|0|0/LC=65535|65535|65535
```

Sent after [71/00 CvEnter](71.md#7100-cventer). The client adds the three
award amounts to the `PP` balance itself, clamps at 99,999 and shows the
announcement; it then shows the `LC` models as Lucky Cards. The table the
client reads their display from is not recovered (unverified).

### Auction collection

```c
struct ShopInit;          // the shop body above
```

```
S2C GTM0GB2001300@Init=/N=2/RA=0/M=10000/CP=35/S=3/SP=0/SN=/CMP=0/HD=0
```

Sent directly after [B0/01 ShReq](B0.md#b001-shreq) as the entry
acknowledgement. It is followed by [B2/20 Data](#b220-data) and
[B2/21 Card](#b221-card).

### Event cards

```c
struct EcmInit {
    uint32_t N;                       // session number, 1..255
    uint32_t RA;                      // rating
    int32_t  M;                       // money before this visit; negative values clamp to zero
    uint32_t CP;                      // collection points
    uint32_t S;                       // owned card count
    uint32_t RT;                      // purpose unknown (unverified)
    uint32_t PM;                      // money credited by this visit
    uint32_t C;                       // incoming card count, 0..9
    struct { struct Card D; } N[9];   // sections N0..N(C-1), one eight-field card each
};
```

```
S2C GTM0GB2001300@EcmInit=/N=1/RA=300/M=10000/CP=5/S=12/RT=0/PM=500/C=2@N0=/D=12|3|0|4|5|6|7|255@N1=/D=...
```

Sent by the event card service after a positive
[91/00 CardEnt](91.md#9100-cardent). `struct Card` is defined in
[rules.md](../../client/rules.md#card-record). The client shows at most
nine cards, so a visit carries at most nine; the body also has to fit the
447-byte body limit. More cards wait for another visit. What the client
does with the body is in
[event-cards.md](../../flows/event-cards.md#sequence).

### Event matches

```c
struct EInit {
    uint32_t N;           // session number, 1..255
    uint32_t RA;          // rating
    uint32_t M;           // money, parsed but not applied to the client's balance
    uint32_t CP;          // collection points
    uint32_t S;           // owned card count
    uint32_t RT;          // purpose unknown (unverified)
    uint32_t Stat;        // 0..3, event flags, purpose unknown (unverified)
};
```

```
S2C GTM0GB2001300@EInit=/N=1/RA=300/M=10000/CP=5/S=12/RT=0/Stat=0
```

Sent by the event match service after [99/00 EInitEnt](99.md#9900-einitent)
with `Ans=1`. The client waits for it and then answers with
[B2/07 CardSelect](#b207-cardselect).

## B2/14 Buy

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| C2S | shop service | session number | `Card` on the same subtype, below | per service, below |

A purchase. A positive `Card` reply carries the generated cards as full
eight-field tuples (`struct Card` in
[rules.md](../../client/rules.md#card-record)); `@Card=/S=0` refuses the
purchase. After a positive Card the client debits its balance locally and
sends [Get](#b215-get).

### Shop

```c
struct Buy {
    uint32_t No;          // pack ID from the visible list
};

struct BuyCard {
    uint32_t S;                       // generated card count, 1..10, the pack's card count; 0 refuses
    struct { struct Card D; } N[10];  // sections N0..N(S-1)
};
```

```
C2S GTM0GB2001401@Buy=/No=2
S2C GTM0GB2001401@Card=/S=3@N0=/D=142|22|1|33|45|9|51|255@N1=/D=34|31|1|13|12|5|75|255@N2=/D=42|42|1|19|9|6|163|255
```

`S=0` is returned for an unknown pack, a pack not in the
[visible list](#shop), or a price above the balance. The client debits its
displayed balance by the catalogue price and holds the cards until Get.

### Prize Center

```c
struct PrizeBuy {
    uint32_t No;          // prize pack ID, 45..74
};

struct PrizeCard {
    uint32_t S;                       // 1; 0 refuses
    struct { struct Card D; } N[1];   // the prize card
};
```

```
C2S GTM0GB2001403@Buy=/No=57
S2C GTM0GB2001403@Card=/S=1@N0=/D=128|65|0|56|35|14|150|255
```

Each prize pack generates one card of a fixed model with the usual
generator (stats, arrows and the 2/256 type promotion vary). `S=0`
refuses an ID outside 45..74 or a price above the point balance. The
client debits the points locally and moves the card into its collection
when it fits.

## B2/15 Get

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| C2S | service of the open session | session number | none, except in the auction collection (below) | `struct Get` |

```c
struct Get {
    uint32_t No;          // session number
};
```

The client sends Get once its working inventory fits 1000 cards; with a
full inventory it first runs the overflow editor, which sends
[Erase](#b210-erase) and [Decks](#b222-decks) edits and then Get. The
working set may hold up to 30 incoming cards beyond the 1000 committed
ones. Event matches do not use Get.

### Shop

```c
struct Get;               // as above
```

```
C2S GTM0GB2001501@Get=/No=1
```

A server commits the staged purchase, including edits received since Buy,
when it receives Get.

### Prize Center

```c
struct Get;               // as above
```

```
C2S GTM0GB2001503@Get=/No=3
```

Get commits the staged card and the point debit. Sell is not part of the
Prize Center.

### Auction collection

```c
struct Get;               // as above
```

```
C2S GTM0GB2001502@Get=/No=2
```

The client sends Get twice. A server answers the first Get with the
won-card pages as [B2/21 Card](#b221-card), and the second Get with the
refund [B2/20 Data](#b220-data) and the [B2/17 Quit](#b217-quit) reply.

### Event cards

```c
struct Get;               // as above
```

```
C2S GTM0GB2001501@Get=/No=1
```

With `C=0` in `EcmInit` no Get is sent. Otherwise the client sends Get
before revealing the cards when they fit the inventory, or from the
overflow editor after its Erase and Decks edits. A server validates the
edits made in the overflow editor, applies the batch to the inventory and
marks those cards claimed. A repeated Get does nothing. Erase with `Mode=2`
is an empty edit.

## B2/16 Sell

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| C2S | shop service | session number | none | `struct Sell` |

```c
struct Sell {
    uint32_t C;                       // record count, 1..15
    struct { struct CardReduced D; } rec[15];   // sections @0..@C-1, one reduced card each
};
```

```
C2S GTM0GB2001601@Sell=/C=1@0=/D=34|31|1|13|12|75
```

Removes one owned copy per record and credits its sale value, capped at
99,999,999. Sent in the shop and the auction collection; the record rules
are in [Erase](#b210-erase).

## B2/17 Quit

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| C2S | service of the open session | session number | `Quit` on the same subtype, below | `struct Quit`, `struct QuitReply` |

```c
struct Quit {
    uint32_t No;          // session number
};

struct QuitReply {
    uint32_t N;           // session number that was closed
    uint32_t D;           // purpose unknown (unverified); 0 observed
    uint32_t B;           // purpose unknown (unverified); 0 observed
};
```

The reply closes the session. A client that did not receive the reply may
resend Quit; a server answers the same reply for the last closed session.

### Shop

```c
struct Quit;              // as above
struct QuitReply;
```

```
C2S GTM0GB2001701@Quit=/No=1
S2C GTM0GB2001701@Quit=/N=1/D=0/B=0
```

The client waits for the reply before leaving the shop.

### Prize Center

```c
struct Quit;              // as above
struct QuitReply;
```

```
C2S GTM0GB2001703@Quit=/No=3
S2C GTM0GB2001703@Quit=/N=3/D=0/B=0
```

Answered as in the shop.

### Auction collection

```c
struct QuitReply;         // as above
```

```
S2C GTM0GB2001702@Quit=/N=2/D=0/B=0
```

The client sends no Quit. A server sends the reply on its own after the
final Data that answers the second Get, and the client waits for it.

### Event cards

```c
struct Quit;              // as above
struct QuitReply;
```

```
C2S GTM0GB2001701@Quit=/No=1
S2C GTM0GB2001701@Quit=/N=1/D=0/B=0
```

The client treats the visit as closed on the reply; when the reply fails
it polls for a `Dead` message. Quit with unclaimed cards (`C` above 0 and
no Get) is an error; a visit with `C=0` may Quit directly. A repeated Quit
of a closed session is answered again with the same reply. `EQuit` is not
used by the event card service.

### Event matches

```c
struct Quit;              // as above

struct EQuit {
    uint32_t D;           // purpose unknown (unverified); 0 observed
    uint32_t Stat;        // 0..3, as in EInit
};
```

```
C2S GTM0GB2001701@Quit=/No=1
S2C GTM0GB2001701@EQuit=/D=0/Stat=0
```

The event match service closes a selection session with `EQuit`, both
after a confirmed `Select` and in answer to a client cancel, which is the
ordinary Quit.

## B2/20 Data

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| S2C | shop service | session number | none | `struct CollectionData` |

```c
struct CollectionData {
    uint32_t M;           // money credited in this stage
};
```

```
S2C GTM0GB2002002@Data=/M=550
```

Auction collection only. `M` is the money credited in this visit: seller
payments in the first stage after Init, refunds in the last stage after the
second Get. The client has no acknowledgement for money, so the credit is
durable as soon as it is sent. The final stage is sent even when `M=0`.

## B2/21 Card

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| S2C | shop service | session number | none | `struct CollectionCard` |

```c
struct CollectionCard {
    uint32_t E;                       // total cards in the stage, 0..30
    uint32_t S;                       // index of the first card in this page
    uint32_t C;                       // cards in this page
    struct { struct CardReduced D; } N[30];   // the cards, N0..N(C-1); numbering restarts at 0 per page
};
```

```
S2C GTM0GB2002102@Card=/E=2/S=0/C=2@N0=/D=142|22|1|33|45|51@N1=/D=34|31|1|13|12|75
S2C GTM0GB2002102@Card=/E=0/S=0/C=0
```

Auction collection only. Pages carry the returned cards (unsold exhibits)
after Init and the won cards after the first Get, as reduced tuples. An
empty stage is `@Card=/E=0/S=0/C=0`. A stage holds at most 30 cards and
each page fits 447 bytes.

## B2/22 Decks

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| C2S | service of the open session | session number | none | `struct Decks` |

```c
struct Decks {
    uint32_t C;                       // record count, 1..13
    struct { uint32_t D[7]; } rec[13];   // sections @0..@C-1: the reduced 6-tuple, then the deck slot to assign (255 clears)
    uint8_t  DN1[17];                 // optional @DN1=/S=, name of deck 1 as hex bytes, at most 17 without NUL
    uint8_t  DN2[17];                 // optional @DN2=/S=, name of deck 2, same form
};
```

```
C2S GTM0GB2002201@Decks=/C=2@0=/D=42|42|1|19|9|163|0@1=/D=142|22|1|33|45|51|255@DN1=/S=4465636B204F6E65
```

The message assigns the slot to each record's card, and any other card
holding that slot is cleared. A Decks message carries at most one of
`@DN1` and `@DN2`. The same body is sent in the shop, the Prize Center, the
auction collection, the event card claim and the event match selection
session; the record rules are in [Erase](#b210-erase).
