# 42 Chat

Named chat has two halves. Membership is negotiated with the
[room service](../services.md#room-service) over `GTM0G42` messages: entry,
acknowledgement and roster pages, for the room roster after room entry and
for the table roster after table admission. Text is relayed over ordinary
IRC PRIVMSG or NOTICE, either to a channel (public) or to a nick (private),
with a `GTM0G42` payload. Names on the wire are raw bytes in the Windows
CP932 code page; the limits below are bytes, not characters. The relay
rules a server applies to peer traffic are in
[envelope.md](../envelope.md#relay-guard).

## 42/01 Chat entry

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| C2S | room service | 0 | [42/02 Chat acknowledgement](#4202-chat-acknowledgement) | `struct ChatEntry` |

```c
struct ChatEntry {
    uint64_t NN;   // the account's nickname identity, sixteen hex digits
};
```

```
C2S GTM0G42000100@Chat=/NN=0000000000000001
```

The client sends entry to the roster it wants: the room roster after room
entry, the table roster after table admission. Membership starts with entry
and ends when the client PARTs the matching channel, is removed from the
table, or disconnects. A repeated entry returns the current roster without a
new counter value.

## 42/02 Chat acknowledgement

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| S2C | room service to the entering client | 0 | none | `struct ChatAck` |

```c
struct ChatAck {
    uint32_t EN;   // 1 accepted
};
```

```
S2C GTM0G42000200@Chat=/EN=1
```

After `EN=1` the service sends the roster pages of
[42/04](#4204-chat-roster) to every member of that group.

## 42/04 Chat roster

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| S2C | room service to every member of the group | index of the last page, the same on every page of one roster | none | `struct ChatRoster` |

```c
struct ChatRoster {
    int32_t  C;         // roster counter, increasing with every change to the group
    uint32_t Num[2];    // page index, then member count on this page
    uint64_t NN[8];     // member identities, `|` separated
    uint8_t  CN[8][16]; // member display names as hex bytes, `|` separated
};
```

```
S2C GTM0G42000400@Chat=/C=1/Num=0|1/NN=1122334455667788/CN=82A0
```

Pages are sent in ascending order. A body is at most 447 bytes and a roster
at most 17 pages; at maximum name length that is eight members per page.
The client keeps each identity as the full qword even when two display
names collide after shortening.

## 42/08 Chat text

| Direction | Service | Argument | Reply | Body |
| --- | --- | --- | --- | --- |
| P2P | relayed | status: 0 public, sent to a channel; 1 private, sent to a nick | none | `struct ChatText` |

```c
struct ChatText {
    int32_t La;       // locale
    char    Dt[422];  // `#CHAT#`, the sender's display name, TAB, then the text
};
```

```
P2P GTM0G42000800@Chat=/La=1/Dt=#CHAT#Alice\thello /x=@y
P2P GTM0G42000801@Chat=/La=2/Dt=#CHAT#Alice\tprivate
```

`Dt` holds what the 447-byte body leaves after `@Chat=/La=` and `/Dt=`.
Everything after the TAB is opaque text: slashes, at signs and CP932 bytes
are not field separators.

The sender copies its complete character name before the TAB. The receiving
client accepts a name of 1..15 bytes and rejects a 16-byte name before the
TAB, so a client whose canonical name fills all 16 bytes cannot be displayed
by other clients unless the relay shortens it. The client accepts `82 A0`
(one two-byte character) as a complete name, and a 15-byte name ending in a
lead byte `82`, while rejecting the 16-byte spelling of the same name. A
server that shortens a 16-byte name to 15 may therefore cut a multibyte
character in half, and nothing in the client prevents that.

The same 16-byte name field and 15-byte display limit apply across the
lobby: `GameML` and `PLAYACK` keep `MLNN` and `HN` in terminated 16-byte
fields, `VsGameInit` copies `CN` into 16-byte slots without a bound, and the
room `DE` and `PD` records serialize a 16-byte name together with the bytes
after it (see [L.md](../L.md#de-enter)). Distinct accounts whose names share
the same 15-byte prefix remain distinct on every path, because the client
selects members by `NN`, `MLID` or character identity, never by the
displayed name.

Server choice: relay the text unchanged but replace the name before the TAB
with the authenticated account's first 15 name bytes, and reject names with
C0 control bytes or DEL.
